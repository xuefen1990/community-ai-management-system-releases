# 单位主账号与子账号权限实施计划

日期：2026-09-23  
依据：[已确认设计](../specs/2026-09-23-unit-account-direct-members-and-permissions-design.md)  
状态：本地实现与自动测试已完成；图形预览检查及 ECS 同步待完成。

## 原则

- 沿用单位 ID、已启用成员、现有业务数据、单位 AI 余额和历史流水，不重建单位。
- 先完成并验证新流程，再撤除邀请码申请及重复成员管理代码。清理只限确认无引用的程序路径；历史申请、审计、额度记录不删除。
- 既有工作区有大量其他未提交改动。每一步先检查目标文件的当前差异，只处理本任务相关内容，不重置或覆盖其他改动。
- 后端变更按项目约定完成本地检查、相关测试、仅同步本次必要文件至 ECS、重启受影响服务，并检查健康接口及实际登录入口。开发预览使用 `npm run dev`；没有正式发布请求时不打包或登记更新。

## 阶段 1：账号与首次登录

1. 在后端账号服务和路由加入“单位管理员直接创建成员”“管理员重置成员初始密码”。校验管理员角色、同单位、手机号唯一、单位有效状态和输入格式。密码由后端安全生成、哈希保存，只在创建或重置响应中返回一次；日志与审计不写明文。
2. 为新建或重置的成员保存“首次登录须改密”状态。登录接口明确返回该状态；受保护的业务和 AI 请求在改密前拒绝，个人改密与退出登录仍可用。改密后更新会话版本，旧令牌失效。既有成员不受此状态影响。
3. 补后端测试：非管理员或跨单位创建、重复手机号、初始密码一次性展示、首次改密拦截、改密后旧令牌失效、到期后全单位成员无法访问且续期恢复。

主要涉及 `backend/src/services/authService.js`、`backend/src/routes/authRoutes.js`、`backend/src/middleware/auth.js`、`backend/src/database.js` 和相关后端测试。

## 阶段 2：统一权限判定

1. 建立与实际业务导航、共享数据键和 API 对应的权限目录。岗位预设只用于创建时填充；账号保存逐人权限。后端拒绝不在目录中的模块和动作，权限更新写审计并使已登录成员及时获得新权限。
2. 对共享工作区读取、写入和订阅逐模块校验。查看权限是创建、修改、删除和导出的前提；未知键默认拒绝。梳理所有业务接口和 Electron IPC，确保菜单隐藏之外的实际操作也受控，资金确认、批量导出等敏感动作单独校验。
3. 将 AI 使用设为独立开关，在在线 AI 接口和 Electron 主进程的本地/在线 AI 调用入口校验；关闭后不扣单位 Token，普通非 AI 公文操作仍按公文权限处理。
4. 补“只读无法修改、未授权不可读取、权限撤销立即生效、同单位成员可读获权全部记录、跨单位拒绝、AI 开关独立于 Token 余额”测试。

主要涉及 `backend/src/services/unitWorkspaceService.js`、`backend/src/routes/aiRoutes.js`、`backend/src/services/aiService.js`、`app/src/main/ai-router.js`、`app/src/main/ai-assistant-service.js`、`app/src/main/ipc-handlers.js` 及相关业务入口。具体文件以权限目录核对结果为准。

## 阶段 3：主账号管理界面与登录体验

1. 把成员管理整合为一个页面：单位授权与 Token 摘要、成员搜索和列表、新增成员、岗位预设、逐板块权限、AI 开关、停用恢复、重置密码及成员用量。
2. 创建成功后一次性展示手机号和初始密码。成员首次登录进入改密页，成功后回工作台；登录失败和授权过期给出清楚中文提示。
3. 由当前账号权限决定导航、快捷操作、按钮和入口是否展示；权限变更后刷新界面状态。保留后端与主进程拒绝作为最终校验。
4. 补渲染进程、预加载和 IPC 合约测试，覆盖权限矩阵、首次改密、隐藏入口和账号管理操作。

主要涉及 `app/src/renderer/js/local-auth-ui.js`、`app/src/renderer/style.css`、`app/src/main/remote-auth-service.js`、`app/src/preload/index.js`、`app/src/shared/ipc-contract.js` 和相应测试。

## 阶段 4：旧流程迁移与清理

1. 切换前列出待审核成员申请。已启用成员保持原账号和权限；待审核申请由管理员完成处理或明确作废并留审计，不静默删除。
2. 新流程验证通过后，撤下“邀请码加入单位”、邀请码管理与审核申请界面，合并旧成员管理弹窗和整页。逐项检查调用者后移除不再使用的服务、IPC、路由、样式和专属测试断言；历史数据集合保留为只读档案。
3. 对现有单位、成员、额度与旧申请数据做兼容测试，验证清理不会改变登录、余额或历史审计。

## 阶段 5：验收与交付

1. 在开发版用一个主账号和多个子账号走通新增、首次改密、只读、修改、隐藏板块、AI 关闭、软件到期与续期、Token 用尽等关键流程。
2. 运行相关后端和桌面端测试，检查最终差异及 `git status`，确认没有夹带无关改动或凭据。
3. 后端实际改动同步 ECS 并验证服务、健康接口、登录与权限结果。向用户报告实际完成范围和遗留问题；本轮不触发正式应用更新或 GitHub 上传。
