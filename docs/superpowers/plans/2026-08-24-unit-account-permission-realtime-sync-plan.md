# 村居单位账号、权限与实时同步实施计划

> 设计依据：[单位账号、权限与实时同步设计](../specs/2026-08-24-unit-account-permission-realtime-sync-design.md)

## 实施原则

以可独立验证的纵向切片推进。先让“单位申请、成员加入、审核、有效期继承和权限校验”可在后端完整运行，再替换桌面端登录；业务数据同步随后按统一的数据访问层逐模块迁移。旧接口和本机历史数据在迁移完成前保留只读或导入兼容路径，避免静默丢失数据。

## 阶段 1：后端组织与账号基础

1. 将后端数据模型扩展为单位、单位管理员申请、成员申请、邀请码、成员权限和审计记录；为用户增加所属单位、账号状态和成员角色字段，并为旧的系统管理员记录做兼容迁移。
2. 把认证状态判断收敛为一个后端函数：平台管理员永久有效；单位管理员需已启用且未到期；成员还必须满足“本人已启用、所属单位已启用、单位管理员有效”。所有登录、令牌验证和受保护接口复用此判断。
3. 增加公开的单位管理员申请、成员加入申请接口；增加平台审核单位管理员、单位管理员审核成员、生成/作废邀请码、设置权限和续期/停用的接口。
4. 令牌和接口返回值携带必要但最小化的单位、角色和权限摘要；密码哈希、邀请码原文和其他敏感字段不得返回。
5. 为上述状态转换、跨单位拒绝、管理员到期同步禁用成员和审计记录编写后端自动化测试。

## 阶段 2：桌面端认证体验

1. 在保留账号服务器设置入口的前提下，重做登录卡片为“账号登录、申请单位管理员、申请加入单位”三个入口。
2. 加入单位使用邀请码或二维码承载的邀请码；客户端只把邀请码和申请资料提交给后端，不自行判断单位归属或权限。
3. 登录后的会话状态显示真实姓名、单位、角色和有效状态；明确展示待审、停用、到期和无权限原因。
4. 增加单位管理员的成员申请处理、邀请码管理和权限分配界面；平台审核界面继续位于服务器管理后台。
5. 补充 RemoteAuthService、预加载桥接和渲染层测试，验证失败不会创建本机孤立账号。

## 阶段 3：共享业务数据层与实时通知

1. 用服务器共享数据存储替换桌面端本机 JSON 作为业务数据权威来源；所有业务记录补充单位、创建者、最后修改者和版本字段。
2. 建立统一的后端数据 API 和权限中间件，确保每个读写操作都按单位隔离、按模块和动作授权。
3. 使用服务器推送通道向同单位且有查看权限的在线客户端广播版本变更；客户端接到通知后重新获取对应模块数据。
4. 写入请求携带预期版本号；版本不一致时返回冲突信息，客户端提示刷新，禁止静默覆盖。
5. 逐模块迁移人员、走访、党务、土地、证明、公文和工作管理数据；每迁移一个模块，补充分单位、权限和并发修改测试。

## 阶段 4：迁移、验证与发布

1. 为旧版本机 JSON 提供管理员确认后的导入工具，将数据显式导入指定单位并形成审计记录。
2. 在两台桌面端设备上完成联调：成员审批、权限调整、管理员到期/续期以及跨设备实时更新。
3. 运行后端、桌面端和新增端到端测试；验证旧登录、服务器不可达、过期邀请码、跨单位访问和并发写入等异常路径。
4. 仅提交本次相关文件，推送当前分支，并在发布说明中列明迁移前备份要求和已迁移模块。

## 首个交付切片

本轮先完成阶段 1 的后端组织与账号基础，并以自动化测试证明权限和有效期链路正确。随后接入阶段 2 的登录页；阶段 3 按业务模块分批实施，不与账号模型变更混在同一提交中。
