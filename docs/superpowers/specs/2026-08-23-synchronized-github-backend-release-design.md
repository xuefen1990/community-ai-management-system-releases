# GitHub、后端与客户端同步发布设计

## 目标

将每次桌面端发版收敛为一次发布操作，同时完成：

1. 创建 GitHub Release，上传 DMG、自动更新 ZIP 和 `latest-mac.yml`；
2. 将同一 DMG、版本号和更新说明上传并保存到账号后端；
3. 客户端启动时从已配置的账号后端获取版本信息，发现新版本后提示用户，并通过 GitHub 的标准更新通道下载与安装。

当前登录与启动修复作为 `0.3.1` 首次采用此流程。

## 架构

### 统一发布命令

新增发布脚本，由一个明确的版本号和更新说明驱动：

1. 校验应用版本与发布版本一致，生成 ARM64 DMG、更新 ZIP 和更新清单；
2. 创建或更新对应 GitHub Release，上传三个发布资产；
3. 使用发布环境提供的后端管理员凭据登录后端；
4. 调用后端版本发布接口，将同一 DMG、版本号、平台、稳定渠道和更新说明上传到后端；
5. 验证 GitHub Release 资产和后端最新版本记录均为该版本后，输出发布结果。

后端地址与管理员凭据仅从发布环境变量读取，不写入源码、配置样例或 Git 提交。

### 后端版本记录

后端继续保存完整 DMG、文件摘要、大小、下载记录和更新说明。版本记录增加 GitHub Release 下载地址，用于对照和诊断；客户端仍使用 GitHub 的 ZIP 与更新清单完成自动更新。

同一平台和渠道不允许重复发布同一版本，避免一个版本对应多份不一致的安装包。

### 客户端检查与提示

桌面端新增后端版本检查器：

1. 从已保存的账号服务器地址读取后端；
2. 以当前应用版本查询后端 `/api/update/check`；
3. 后端确认有更新后，调用现有 GitHub 更新检查；
4. 仅当 GitHub 也提供同版本或更新版本时，显示现有“发现新版本”提示；用户确认后按现有机制下载并重启安装。

后端不可用或两端版本不一致时不阻塞软件使用，也不下载不一致的版本；客户端记录可理解的检查失败状态，手动检查可重试。

## 失败处理

- GitHub 发布失败：不上传后端，发布命令直接失败。
- 后端上传失败：保留已创建的 GitHub Release，不自动删除；命令输出明确的补传操作，防止误删已发布版本。
- 客户端后端检查失败：不影响登录和工作台；显示“暂时无法确认后端版本”，并保留手动检查。
- 后端与 GitHub 版本不一致：不弹出下载/安装，避免客户端取得未同步版本。

## 验证

1. 后端测试覆盖版本唯一性、发布记录的 GitHub 地址和版本检查返回值。
2. 桌面端测试覆盖后端有更新、无更新、后端异常及两端版本不一致时的行为。
3. 构建 `0.3.1` 安装包并运行统一发布命令，验证 GitHub Release 与后端版本列表均包含同一版本和完整 DMG。
4. 使用已安装的旧版本启动，确认收到更新提示、下载并重启安装后升级到 `0.3.1`。

## 范围

修改桌面端更新服务和提示界面、后端版本发布/查询接口、发布脚本与相关测试。账号授权、登录、业务数据和现有 GitHub 自动更新资产格式保持不变。
